# 개인 환경 설계: AssignmentEnv

## 1. 무엇을 결정하는 환경인가?

예를 들어 80mm 길이의 적층 선을 20mm 구간 4개로 나누어 놓는다.
매 단계에서 다음 구간을 로봇 1, 2, 3 중 누구에게 맡길지 선택한다.
환경은 선택한 로봇의 이동·적층·복귀와 필요한 대기 시간을 계산하고 안전 여부를 검사한다.
모든 구간을 배정하면 경로를 CSV로 내보내 최종 검증한다.

환경은 문제의 규칙이고, PPO는 이 환경에서 배정 방법을 학습할 수 있는 알고리즘이다.
이번 주에는 PPO 없이 고정 규칙으로 환경의 동작부터 확인했다.

## 2. 팀 참고 환경과 비교

| 항목 | 팀 gym_wrapper.py | 개인 AssignmentEnv |
|---|---|---|
| 결정 | 3대의 목표 XYZ와 T/D/W/F | 다음 구간을 맡을 로봇 번호 |
| 행동 | 연속값 (3,4), 총 12개 | Discrete(3): 0/1/2 |
| 관측 | 로봇별 시간·XYZ·모드 (3,5) | 작업 목록·배정 이력·로봇 정보·진행도 |
| 이동 경로 | 정책이 목표 좌표를 제안 | home→시작점→끝점→home |
| 시간 처리 | 한 단계의 가장 느린 로봇까지 동기화 | 각 로봇 일정에 작업을 삽입, 안전하면 병행 |
| 충돌 | 실행된 단계에 벌점 | 안전한 후보 출발 시각을 찾고 없으면 실패 종료 |
| 완료 | 로봇 3대 모두 F | 모든 작업 배정 완료 |
| 장점 | 좌표와 적층 경로 선택의 자유도 | 행동이 단순하고 배정 효과를 해석하기 쉬움 |
| 제약 | 유효한 좌표·모드를 탐색해야 함 | 경로 형상과 작업 순서는 미리 고정 |

같은 문제 전체를 동일한 자유도로 푸는 환경은 아니다. 개인안은 **작업 배정·일정 문제로 범위를 줄인 환경**이다.
팀에서 경로 자체 생성도 필수로 요구한다면 이 환경만으로 그 요구를 충족하지 못한다.

## 3. 상태/관측

float32 1차원 벡터이며 작업이 N개이면 `11N+32`개 값이다. 샘플 N=4이면 76개이다.

| 구성 | 개수 | 내용 |
|---|---:|---|
| 전체 진행도 | 1 | 완료 작업 수 / 전체 작업 수 |
| 각 작업 | 11N | 시작XYZ 3, 끝XYZ 3, 배정 여부 1, 배정 로봇·출발·소요·복귀 시간 4 |
| 각 로봇 | 27 | baseXYZ 3, homeXYZ 3, 도달 반경·팔 반경·TCP 반경 3 × 로봇 3대 |
| 공정/전체 일정 | 4 | 적층 속도, 이동 속도, 팔 여유 거리, 현재 makespan |

좌표는 시나리오 크기 기준, 시간은 `time_scale` 기준으로 나눈다.
`time_scale`은 각 작업을 가장 느린 로봇으로 왕복했을 때의 소요 시간 합(최소 1초)이다.
배정 로봇은 `(robot_id)/3`으로 표시하고 아직 배정하지 않은 값은 0이다.
고정 시나리오 안에서 작업 좌표와 배정 이력을 함께 제공해, 과거 일정의 정보를 남긴다.
STL 전체 형상·서로 다른 config의 모든 옵션을 벡터에 담는 일반화 환경은 아니다.

## 4. 행동과 시간

행동 0 → 로봇 1, 행동 1 → 로봇 2, 행동 2 → 로봇 3.
작업 순서는 JSON 입력 순서로 고정하며 층 높이가 감소하면 거부한다.
구간은 같은 Z에서 진행되는 길이가 0보다 큰 직선이다.

이동 시간 = 3차원 이동 거리 / travel_speed_mm_s.
적층 시간 = 구간 길이 / deposition_speed_mm_s.
로봇은 작업마다 home으로 돌아온다. 아래층 작업은 복귀까지 끝난 뒤 위층 작업을 시작한다.
복귀와 층 간 대기 규칙은 보수적인 설계이며 최적해를 보장하지 않는다.

## 5. 충돌 처리

배정 후보마다 이미 계획된 모든 로봇의 전체 경로를 함께 검사한다.
대기 중인 로봇과 작업을 끝내고 정지한 로봇도 검사 대상이다.
현재 가능한 시각, 기존 경로의 절점 시각들, 현재 makespan을 후보 출발 시각으로 사용한다.
그중 가장 이른 **검사 통과 후보**를 채택한다. 연속 시간 전체에서 최적의 시작 시각을 찾는 것은 아니다.

팀 검증기의 충돌 기준은 XY 평면이다. base→TCP 선분에 팔 반경을 적용한 영역끼리의 거리와
TCP 중심 사이 거리를 비교한다. 팔끼리는 두 팔 반경에 clearance를 더하고, TCP끼리는 두 반경의 합을 쓴다.
따라서 Z를 높였다는 이유만으로 충돌이 없어지지 않는다.
검사는 설정된 시간·이동 간격으로 보간한 표본에 기반하므로 실제 장비의 연속 3차원 충돌 검증을 대신하지 않는다.

충돌 후보는 실행하지 않고 다른 출발 시각을 찾는다. 모두 불가능하면 -2점으로 실패 종료한다.
이 설계는 안전한 일정 후보만 받아들이는 방식이다. 정책이 위험한 움직임을 직접 반복하면서 회피 경로를 학습하는 방식은 아니다.

## 6. 보상과 종료

```text
후보가 불가능한 경우: reward = -2, terminated = True
후보가 가능한 경우: reward = -(새 makespan - 이전 makespan) / time_scale
모든 작업 배정 완료: 위 보상에 +1
truncated = False (작업 수 N으로 에피소드 길이가 유한함)
```

할인 없이 합하면 완료 에피소드의 누적 보상은 `1 - 최종 makespan / time_scale`이다.
같은 시나리오·작업 목록에서는 makespan이 짧을수록 보상이 크다.
향후 PPO 사용 시 이 목적을 그대로 유지하려면 gamma=1을 고려한다.

**배정 완료 보너스는 최종 형상 PASS 보너스가 아니다.**
작업 목록 자체에 적층 구간이 빠져 있어도 배정은 완료될 수 있다.
그래서 제출 평가와 환경 비교는 반드시 export 뒤의 `run_validation.status`로 판단한다.
형상 자동 생성이나 작업 목록의 정확성을 학습 목표로 삼으려면 종료 보상 설계를 추가해야 한다.

## 7. 최종 평가

원본 config.yaml, target.stl을 그대로 복사하고 환경이 만든 trajectory.csv를 저장한다.
`run_validation(input_dir, output_dir)`이 도달 범위, 충돌, 형상, 경로 규칙을 평가한다.
CSV의 mode는 T=이동, D=적층, W=대기이며 현재 행에서 다음 행까지의 동작이다.
세 로봇 모두 0초에 시작하고 최소 2행, 마지막 W를 갖는다.

각 알고리즘의 `experiment.json`에는 선택 행동·보상·시간·검증 요약을 함께 기록한다.
입력 config/STL의 SHA256도 기록하므로 비교 조건이 같은지 확인할 수 있다.
