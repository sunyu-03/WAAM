# 경로 PPO와 여러 입력 학습 개발 결과

저장 위치: `C:\Users\User\Desktop\AInAlgorithm\waam_generalization\integration`. 새 실행 코드는 **train_routes.py**, 환경은 **algorithm/environment/route_ppo_env.py**다. v1의 train.py, 팀원 코드, 기존 성공 체크포인트와 6개 모델 결과는 보존했다.

## 구현한 동작

- PPO가 로봇, 후보 작업, 진행 방향을 선택한다. 로봇별 가까운 도달 가능한 작업 두 개와 양방향으로 총 12개 행동을 제공한다. 가까운 작업의 두 방향 모두 불가능하면 다음 작업을 탐색한다.
- 작업 끝 위치를 유지하며 다음 작업을 연결한다. 각 로봇의 홈 복귀 경로를 임시 예약하고, 그 로봇에 다음 작업을 배정할 때 예약된 마지막 복귀를 교체한다. 이미 완료한 작업 경로와 다른 로봇의 예약 경로는 유지한다.
- 현재 레이어의 전체 예약을 공식 궤적·도달·샘플링 충돌 검사로 확인한 후보만 mask에 넣는다. 후보 시작 시간은 작업 완료와 예약 완료 이벤트에서 찾는다. 연결이 불가능하면 모든 예약 복귀가 끝난 뒤 홈에서 시작하는 후보를 검사한다.
- 서로 다른 로봇의 시간 구간을 겹쳐 계획할 수 있다. 레이어가 바뀌면 모든 예약 복귀가 끝난 시점에 맞추고 새 레이어를 시작한다. 레이어 안의 위치 유지와 레이어 간 홈 복귀를 구분한다.
- 학습 입력 여러 개를 에피소드마다 선택한다. 학습 데이터 계약과 평가 입력을 분리하여 학습에 없던 STL/config/task 목록을 평가할 수 있다.
- 저장 모델을 다시 읽어 **모든 작업**의 trajectory.csv를 내보낸 뒤 공식 Validator 1.0.1로 최종 판정한다. mask 검사만으로 전체 형상 PASS를 주장하지 않는다.

이 환경은 오프라인 경로 계획이다. 임시 복귀 예약을 수정하는 행동을 이미 움직이는 로봇에 실시간 명령으로 보내는 방식은 아니다. 충돌 보장은 공식 Validator의 샘플링 규칙 범위이며, 연속 시간의 수학적 무충돌 증명은 아니다.

## 실제 학습과 평가

공식 sample_job에서 유도한 서로 다른 STL 두 개(한 적층 선, 떨어진 두 적층 선)를 학습했다. 학습에는 각각 작업 4개를 사용했다. 평가는 작업 8개인 단일 선, 위치를 바꾼 작업 6개의 두 선, 같은 평가 형상을 2층으로 만든 작업 12개, 공개 Model 06으로 분리했다. 평가 형상 두 개의 STL 해시는 학습 형상과 다르다. 공개 Model 06은 학습에 포함하지 않았다.

| 평가 입력 | 무작위 초기화 PPO 1,024스텝 (s) | 비용 초기화 + PPO 512스텝 (s) | 같은 디코더 Greedy (s) |
|---|---:|---:|---:|
| 단일 선, 8개 작업 | 31.401 | 31.401 | 30.470 |
| 별도 두 선, 6개 작업 | 43.696 | 36.052 | 35.015 |
| 별도 두 선, 2층/12개 작업 | 87.374 | 72.087 | 70.013 |
| 공개 Model 06, 51층/775개 작업 | NOT_RUN | **6,198.823** | **5,649.969** |

표의 실제 실행은 **모두 공식 PASS**다. 초기화 정책의 결과를 PPO가 처음부터 배워 얻은 성과로 해석하면 안 된다. 첫 무작위 초기화 PPO는 주로 한 로봇을 선택했다. 비용 초기화 PPO는 별도 두 선에서 **26.389초**, 2층에서 **52.759초** 동안 두 로봇이 동시에 움직이는 경로를 생성했고 공식 PASS를 받았다. 이 지표는 이동 또는 적층 동작이 겹친 시간이며 적층만의 동시 시간은 아니다. 공개 Model 06에서는 실제 동시 이동 시간이 0초였다.

비용 초기화는 후보의 예상 makespan과 작업 완료 시간을 음수 logit으로 주는 명시적인 Greedy 비용 사전값이다. actor는 선형층, critic은 [64,64] MLP로 시작한 뒤 실제 PPO로 업데이트했다. 초기값과 저장된 actor parameter가 달라졌음을 검사했다. 따라서 경로 선택 능력과 PPO 학습은 연결되어 있지만, 학습만으로 Greedy를 능가했다는 결과는 없다.

작은 형상의 학습 성공이 공개 모델 성능 향상을 보장하지 않았다. Model 06의 **보존된 기존 레이어 Greedy는 5,563.401692초**로 두 새 결과보다 빠르다. 기존 기록을 바꾸지 않았고 별도 benchmark_registry.json에 새 결과와 NOT_RUN 상태를 저장했다. 다른 5개 공개 모델의 v2 PPO 전체 평가와 6개 모델을 사용한 실제 혼합 학습은 아직 실행하지 않았다. 모든 6개 입력은 평가 manifest에서 올바른 작업 수로 로드되는 것을 확인했다: 2,442 / 7,088 / 3,894 / 4,450 / 64,919 / 775.

## 재개와 재현 근거

- 계약 ID: `waam-route-reservations-v2`, 고정 관측 175개 / Discrete(12). v1의 관측 16개/Discrete(3)와 기존 성공 모델의 관측 13개는 직접 연결하지 않는다.
- 관측: 전체 진행과 레이어/시간 정보, 로봇별 작업 위치·시간, 후보별 mask/시작·끝 XYZ/시작·완료·makespan/작업 번호 비율/길이/레이어. 좌표는 시나리오 좌표 범위, 시간은 시나리오의 순차 왕복 시간 상한으로 정규화한다. 과거 전체 경로는 관측에 넣지 않으므로 완전한 Markov 관측이라고 주장하지 않는다.
- 보상: makespan 증가량의 음수 / 시간 상한. 유한 에피소드의 최종 makespan 합산을 목표로 gamma=1, GAE=.95, lr=3e-4, entropy=.005, rollout=128, batch=64, epochs=5, CPU 1 thread, seed=42.
- 혼합 학습은 두 입력을 모두 선택했다. 무작위 초기화 실행의 에피소드 시작 수는 130/127이다. 입력 파일과 작업 목록의 해시·내용을 checkpoint manifest에 기록한다. 평가 목록은 학습 계약을 변경하지 않는다.
- 비용 초기화 모델을 **512 → 640스텝**으로 재개했다. optimizer step은 **40 → 50**, 가중치가 실제 바뀌었고 세 작은 평가 입력은 다시 PASS였다. 혼합 입력 선택 sampler의 RNG도 저장·복원한다. SB3가 첫 reset에서 seed를 다시 적용한 뒤에도 저장 sampler 상태를 사용함을 검사했다.
- 정책·optimizer·전체 스텝·전역 RNG·입력 선택 RNG를 복구한다. 일부 계획한 에피소드는 복구하지 않고 새 rollout으로 reset하므로 중간 시점의 비트 단위 연속 실행은 아니다.
- 첫 random_init 체크포인트는 sampler 저장 보완 전의 시험 기록이다. 이 파일을 재개하면 sampler는 새로 시작한다. sampler 복구 검증은 cost_prior와 resume 체크포인트에 대해 수행했다.
- 기존 파이프라인/순차 PPO/새 경로 테스트 **17개 PASS**. 별도로 체크포인트 재개, actor 업데이트, sampler 복원, 바뀐 학습 데이터와 v1 체크포인트 거부를 실제 파일로 확인했다. 기존 두 성공 ZIP의 SHA256은 이전 값과 동일했다.
- 모든 학습·재개 및 공개 PPO 평가의 source_changed_during_run은 false였다. 실행 경과 시간에는 호스트 대기 시간이 포함될 수 있어 학습 속도 벤치마크로 사용하지 않는다.

근거는 `evidence/routes_20261009_001/`에 보관했다. inputs에는 STL/config/tasks와 dataset/public06/public_all manifest가 있다. random_init, cost_prior, resume, public06_greedy, public06_ppo에 실제 실행 기록·체크포인트·학습 CSV·공식 보고서·최종 궤적이 있고 verification.json은 파일과 optimizer 검증 결과다. 라이브러리는 기존 `.deps`와 `ppo_runtime.lock`을 사용하며 추가로 기존 성공 환경에 설치한 패키지는 없다.

## VS Code에서 실행

현재 integration 폴더에서 **train_routes.py**를 열면 새 학습 코드를 볼 수 있다. F5 목록에 **WAAM PPO v2: 혼합 학습 + 별도 형상 검증**을 추가했다. 새 결과 폴더 이름을 입력한다. 인자가 같은 터미널 실행은 확인했으며 F5 UI 자체는 직접 시험하지 않았다.

```powershell
Set-Location 'C:\Users\User\Desktop\AInAlgorithm\waam_generalization\integration'
$waamPython = 'C:\Users\User\Desktop\WAAM_Validator-main\.venv\Scripts\python.exe'
& $waamPython train_routes.py --dataset evidence/routes_20261009_001/inputs/dataset.json --cost-prior --timesteps 512 --out runs/my_routes_001
```

저장된 비용 초기화 모델에서 이어 학습:

```powershell
& $waamPython train_routes.py --dataset evidence/routes_20261009_001/inputs/dataset.json --resume evidence/routes_20261009_001/cost_prior/ppo_routes.zip --timesteps 128 --out runs/my_routes_resume_001
```

학습 입력을 유지하면서 별도 공개 입력만 평가:

```powershell
& $waamPython train_routes.py --dataset evidence/routes_20261009_001/inputs/dataset.json --eval-dataset evidence/routes_20261009_001/inputs/public06.json --resume evidence/routes_20261009_001/cost_prior/ppo_routes.zip --eval-only --ppo-only --out runs/my_public06_eval_001
```

public06.json을 **public_all.json**으로 바꾸면 6개 전체 모델을 평가한다. ppo-only를 빼면 같은 디코더의 Greedy도 계산한다. 각 case를 완료할 때마다 기록을 저장하고 최종 공식 FAIL이면 비정상 종료 코드와 결과를 남긴다. 저장 경로는 항상 새 폴더여야 한다. ZIP과 같은 이름의 .json/.rng.json을 함께 보존한다. `--cost-prior`는 새 모델에만 적용하며 재개에는 사용할 수 없다.

manifest version 1의 train/evaluation 목록에는 name, job, 선택적인 tasks_json을 넣는다. 경로는 manifest 기준이며 name은 안전한 영문·숫자·하이픈·밑줄만 허용한다. tasks_json을 생략하면 STL/config로 Task Generator를 실행한다. train에는 원하는 공개 모델 case도 넣을 수 있다. 학습 데이터가 바뀌면 기존 모델의 재개를 거부하므로 새 체크포인트로 시작해야 한다.

## 다음에 필요한 성능 작업

6개 공개 모델을 실제 혼합 학습에 사용하고 별도 시드/입력에서 성능을 비교해야 한다. 현재 두 후보 슬롯과 제한된 시작 이벤트는 탐색 범위를 줄인 선택이며 전역 최적화를 보장하지 않는다. 형상 크기와 작업 수가 크게 다른 입력의 특징 정규화, 후보 선택 모델, 후보 검사 비용을 더 검토해야 한다. 특히 Model 05의 64,919개 작업은 이번에 PPO로 실행하지 않았다. 기존 최선 값을 넘긴 것으로 표시하거나 최적성 증명을 주장하지 않는다.

GitHub 제출은 같은 별도 통합 브랜치의 초안 PR로 진행하며, 팀원 성공 코드에 대한 직접 병합은 하지 않는다.
